Per body inside a chart (12 bodies at one date): 0.126 µs vs. 5.760 µs. With a new date on every call the Swiss Ephemeris cannot reuse per-date work (17.318 µs), so the single-call ratio of 143× is the most favourable case for Zodiacally Ephemeris; the chart rows are the representative ones.

Cold start (load the library and compute the first chart in a fresh process, Node.js start-up excluded; 15 runs, median): Zodiacally Ephemeris 19.20 ms, Swiss Ephemeris 10.39 ms. **The Swiss Ephemeris starts faster.** Counting start-up, Zodiacally Ephemeris is ahead in total time after about 124 charts in one process. *Cause: on first use Zodiacally Ephemeris loads Node's crypto module and reads and verifies the SHA-256 of all 8 MB of tables.*

Limitations: Node.js API comparison on one machine; the Swiss Ephemeris is called through the sweph native addon, which adds a JavaScript-to-C call per function, and a C program calling it directly is not measured. Zodiacally Ephemeris evaluates precomputed apparent longitudes (one polynomial per body; houses use precomputed nutation and obliquity tables); the Swiss Ephemeris computes positions from its data at run time and returns longitude, latitude, distance and their speeds, reusing per-date work when several bodies share a date. Zodiacally Ephemeris covers fewer bodies, house systems and a shorter date range. Speed says nothing about accuracy; see agreement.mjs and horizons.mjs.
